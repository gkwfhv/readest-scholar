# Phase 2：批量封面授权查询修复（2026-10-22）

## 观察与范围

隔离 staging 客户端日志在最近 48 小时内出现 10 次 `URI too long`。原始日志上下文因可能包含 URL 或令牌，未获自动审批放行；因此无法断言这 10 次全部来自同一接口。本次修复针对源码中可确定的风险：书库同步一次最多请求 100 本旧书封面，`/api/storage/download` 虽接收 POST JSON，却把所有文件路径放进 PostgREST `.in('file_key', ...)` 的 URL；旧路径回退查询也一次放入全部书籍哈希。

## 修复和测试

- 服务端把文件路径授权查询和旧路径的书籍哈希回退查询分别拆为每批最多 50 个，保留原有账户过滤、删除记录过滤、缺失文件与签名 URL 行为。
- 测试先在 201 个合成封面路径下失败：原实现只发出一次 `.in(...)` 查询；修复后正常路径与旧路径回退两项定向 Vitest 均通过，且每次查询最多 50 个键。
- Node 24 本机拉取服务器工作树后验证：两项定向测试通过、TypeScript `--noEmit` 通过、两个变更文件的 Biome check 通过。本机只用于验证；编辑与提交在服务器开发目录完成。
- 服务器独立 `scholar-dev-builder` 容器已创建，但锁定依赖安装仍受大包下载超时影响；服务器内的完整构建尚未通过，不能据此认定 staging 故障已修复。

## 后续验收

待服务器依赖安装成功后，在专用编译容器复跑定向测试、类型检查与 Web 构建；再用隔离 staging 的 201 份合成 PDF 复测封面同步和服务端错误计数。此次尚未部署到 staging，也不把 Phase 2 标为整体验收通过。
