# Phase 2：批量下载授权查询修复（2026-10-22）

## 观察与原因

隔离 staging 客户端日志在最近 48 小时内出现 10 次 `URI too long`。原始日志上下文可能包含 URL 或令牌，自动审批未放行读取；因此不能断言这 10 次全部来自同一接口。源码中可确定的风险是：`POST /api/storage/download` 收到 JSON 中的文件路径后，将它们一次放入 PostgREST `.in('file_key', ...)`，而 PostgREST 仍把过滤值编码进 URL；旧路径回退也将全部书籍哈希一次写进 URL。

以同一测试账户的 201 份合成 PDF 路径直接向隔离 PostgREST 查询：201 项的 URL 长约 27,693 字符并返回 HTTP 414；首版固定每批 50 项时，单批长约 7,006 字符并返回 HTTP 502；25 项长约 3,581 字符并返回 HTTP 200。因此“每批 50 项”不足以消除真实夹具上的错误。

## 修复与服务器构建

- 服务端现在同时限制每批最多 25 项和过滤值编码后最多 2,800 字符；文件路径与旧书籍哈希回退均使用此规则。账户、软删除过滤和签名 URL 行为保持不变。
- 测试先在固定 50 项实现下失败 3 项，再在修复后通过。服务器专用 Node 24 编译容器中，3 个相关测试文件的 14 项测试、TypeScript `--noEmit`、变更文件 Biome check 均通过；带 staging 公开配置的 Scholar Web standalone 生产构建退出码为 0。容器限制 8 GiB 内存和 1 核 CPU。
- 本机仅曾拉取并验证首版修复；最终按 URL 长度分批的代码、测试和构建都在服务器完成。没有从本机向 GitHub 推送。

## 隔离运行验收

服务器在 `127.0.0.1:3132` 运行候选版，原 staging Web 保持在 `127.0.0.1:3130`，两者连接同一隔离后端。以现有 201 份合成 PDF 的规范对象路径发起认证的批量签名下载：原 staging 返回 HTTP 200 但可用签名链接 0/201；候选版返回 HTTP 200 且签名链接 201/201。候选版的第 1、101、201 份下载内容与源夹具 SHA-256 全部一致。第二个合成账户针对同一 201 条路径得到 0 个签名链接。候选容器本轮日志未出现 `URI too long`。验收后原 staging 的 Web、Auth、REST/数据库、对象存储四路探针均为 `OK`。

## 限制与后续

本项证明候选版解决此批量下载接口在 201 份真实路径上的 URL 长度问题，但历史 10 次报错的来源未全部定位。候选版仍在临时端口，尚未替换运行中的 staging Web。用户界面一次导入 200+ 文件、夹具留下的重复文件行、200+ 规模的跨 Web/桌面集合编辑与元数据双向修改仍待验收；Phase 2 整体未通过。
