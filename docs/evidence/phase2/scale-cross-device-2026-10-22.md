# Phase 2：201 份合成 PDF 的跨端规模核验（2026-10-22）

## 范围

隔离 Linux staging、经 SSH 隧道访问的 Scholar Web，以及独立 macOS `io.github.gkwfhv.readestscholar` 测试包。测试账户和第二个隔离账户均为本次创建的合成账户，未使用生产资料。测试主机运行已验收的 Scholar Web 版本；本记录不声称新分支已部署。

## 导入与数据契约

- 生成 201 个不同字节的两页合成 PDF。自动化浏览器文件选择器未完成 201 文件的批量提交，因此改走**测试环境的签名上传 + REST 写入路径**；这验证服务端接收与跨端管理，不等于用户界面的批量导入通过。
- 为每份文件写入大写 `PDF` 格式、客户端预期的 `Readest/Books/<book_hash>/<book_hash>.pdf` 路径、JSON 字符串形式的 `metadata`，并触发 Scholar 文献/书籍/文件关联。早期夹具曾使用小写格式、原始文件名和 JSON 对象，造成 Web 下载和同步错误；修复的是全部 201 行合成夹具，未改真实用户数据。这说明直接写入 REST 的夹具必须遵守客户端存储契约。
- 完成修复后的只读复核：第一账户有 203 本书，其中 201 本标题为 `Scholar Scale Paper *`，另 2 本为桌面端已有测试书；`scholar_documents` 与 `scholar_document_books` 各 203 行。`files` 与 `scholar_document_files` 各 402 行，因为夹具修复时保留了 201 个旧文件名对象及 201 个规范路径对象。此重复只属于本次直接写入的测试数据，不能算作文件去重通过。
- 对第 1、101、201 份规范路径 PDF 做签名下载并比对完整 SHA-256，3/3 一致。第二账户的 `books`、`files` 与三个 Scholar 表均为 0 行；无法读取第一账户的指定书籍，3/3 签名下载请求被拒绝，越权写入第一账户 `books` 被拒绝。此结论只覆盖这些表和对象路径，不外推到后续新增实体。
- 最终运行现有四路 staging 就绪探针，Web、Auth、REST/数据库、对象存储均为 `OK`。

## 实际界面

- Web 书库显示合成集合 `Scholar Scale`，`Batch A` 有 100 本，`Batch B` 有 101 本；详情显示合成 DOI `10.5555/scholar-scale.100` 与标签 `synthetic`、`phase2-scale`。[Web 详情](scale-web-detail-2026-10-22.png)。从云端下载后能打开两页 PDF 并显示正文。[Web 阅读器](scale-web-reader-2026-10-22.png)。
- macOS 测试包登录同一账户后，搜索栏显示 203 本，书架最初短暂空白，随后能看到集合及 100 本的 `Batch A` 列表。[桌面书架](scale-desktop-list-2026-10-22.png)。目标详情显示相同 DOI、出版日期、语言、`PDF` 格式及两个标签。下载所得文件与合成源文件的 SHA-256 相同。阅读窗口也曾短暂空白，最终显示 PDF 两页缩略图、正文和第 1/2 页状态。[桌面阅读器](scale-desktop-reader-2026-10-22.png)。这证明最终可用，但加载延迟仍待量化与优化，不能记作性能验收通过。
