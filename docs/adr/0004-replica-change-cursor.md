# ADR 0004：分离副本冲突时钟与增量拉取游标

状态：提案，2026-10-22；实施与故障验收前不得标记 Phase 3 通过。

## 背景

当前 `replicas.updated_at_ts` 同时决定字段以外的文件清单/复活令牌冲突顺序，并作为 `/sync/replicas` 的增量拉取游标。服务端按它排序、严格大于上次值、最多返回 1000 行。由此存在三个独立的数据遗漏风险：

1. 两行具有相同 HLC 时，第一页末尾的 `since > updated_at_ts` 会略过另一行。
2. 同一行的旧离线字段写入可能改变字段内容，但行上的最大 HLC 不增加；其他设备的增量拉取看不到它。
3. 仅为通过服务端一分钟时钟偏差检查而重写行 HLC，会改变文件清单或复活令牌的冲突含义。旧清单甚至可能覆盖新的文件。

开机全量重拉可减轻部分遗漏，不能证明周期性增量同步可靠；超过 1000 行时全量拉取本身也会截断。

## 拟采用的协议

- 保留各字段原 HLC 作为冲突时钟。文件清单与复活令牌分别保存自己的操作 HLC；普通字段写入不再抬高它们的冲突时间。离线旧操作不可单凭当前发送时间宣布为较新的内容。
- 在数据库中给每个账户建立事务化递增的变更序号。写入事务先锁定该账户的计数行，再给变更后的副本赋序号；该锁到提交才释放。因此同一账户的提交顺序与序号一致，回滚也回滚序号分配。任何会修改 `replicas` 的路径都必须经过同一触发器或等效受控 RPC。迁移时在锁表事务中为既有行回填序号并初始化计数行。
- 新拉取接口以服务端变更序号分页，按序号递增，明确返回下一页游标与是否还有数据。客户端按（账户 ID、类型）保存游标，账户切换时不能复用另一账户的进度；逐页持久应用后才提交游标，故障后重拉同一页，应用须幂等。异步加载本地游标不得覆盖本会话已确认的较新值。序号在数据库中为 bigint，API 在序列化前显式转成十进制字符串，不能先让 JSON 解析器把 bigint 当作 JavaScript number；客户端游标按十进制字符串传输，避免整数精度问题。
- 推送仍按账户和行校验。过去的合法离线 HLC 不因时间流逝直接拒绝；将未来时钟、恶意载荷、未知类型单独约束。文件清单/复活令牌若与远端并发，需保存冲突双方，交给明确的冲突界面处理，不能静默把旧内容当作新内容。
- 保留旧接口以兼容已安装客户端；新版客户端只在服务端能力确认后使用新游标。无能力时回退到全量拉取并标明降低保障，不把旧增量接口纳入 Phase 3 验收。

## 验收要求

隔离数据库和双设备测试必须覆盖：同 HLC 的第 1000/1001 行、旧离线字段更新、同一行连续更新、反向提交顺序、重试重复推送、推送成功但响应丢失、服务端在事务内崩溃、客户端应用到一半崩溃、清单与删除/复活并发、不同账户互不可见、账户切换后不复用旧游标、游标异步加载与新值写入的竞态。检查每次恢复后的内容和游标，并在故障后重启服务再次查询。

## 取舍与迁移

序号会增加一列、一张账户计数表及写入时的同账户串行锁，需用 200+ 和更大合成规模压测锁等待与分页成本。已有 `updated_at_ts` 字段和旧接口继续可用，但不再承担新版增量游标职责。正式切换前需对 staging 做备份、迁移、回滚和旧客户端兼容检查。
