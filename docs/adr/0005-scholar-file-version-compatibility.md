# ADR 0005：Scholar 文件版本与旧客户端兼容边界

- 状态：提案；Phase 3 文件协议尚未完成客户端切换和故障验收
- 日期：2026-10-23
- 依据：工程计划 §3.1、§4.1、§7.2 与 ADR 0002

## 问题

旧 Readest 客户端按 `files.file_key` 获取和覆盖同一个对象。已验证的二进制修订若继续写这个键，另一设备的旧 PUT 可以静默覆盖字节；只增加数据库版本表无法防止旧接口重新签发可覆盖的 URL。现有 Scholar 版本函数也仍依赖 `files` 与文献文件映射，删除旧行会级联失去版本元数据。

## 拟采用的过渡协议

1. 版本对象使用独立 UUID 键、只创建的签名 PUT、客户端分块计算 SHA-256、服务端读取实际对象校验。一次写入由账户、`fileId` 和客户端持久化的 `opId` 定位；完整字节验证后才 CAS 更新活动头。失败的 CAS 保留已验证的落败版本，供用户比较和恢复。
2. 新客户端对版本 API 携带协议版本与能力标识，先查询服务端能力再写入。缺少能力时禁止将修订内容静默降级为旧键覆盖；界面明确提示服务器需要升级。客户端必须在离线队列中保留 `opId`、源文件引用和预期活动版本，重新上线后重试同一操作。普通网络错误不能生成新的操作 ID。`412` 只表示对象可能已经存在，仍须完成接口重新校验实际 SHA-256。
3. `files.file_key` 暂作为旧客户端下载别名。文件尚无活动版本时，旧下载走旧对象；一旦有活动头，兼容下载接口应解析到该头的已验证对象，并对旧客户端的再次覆盖请求给出明确升级错误，防止“上传成功但新端看不见”。旧客户端仍可读取版本化文件；旧客户端修改这种文件需要升级。能力与兼容窗口应在发布文档中明确。
4. 配额在迁移期保守计入仍存在的旧对象和所有待完成/已验证版本。删除逻辑先建立墓碑与保留期，不能让旧 `files` 行硬删除级联抹掉可恢复的版本。对象垃圾收集要与数据库状态、签名 URL 有效期和失败重试协调；先完成独立备份及恢复演练，再开放永久删除。
5. 大文件需分块与断点续传。选择具体 multipart 实现前，分别在 Silo/MinIO 与 R2 验证签名、条件写入、续传、取消和遗留分片清理；单次 PUT 只作为当前小文件基础，不作为 Phase 3 大文件验收。

## 当前实现和剩余门槛

迁移 041/042、条件写入、服务端校验、准备/完成/活动与历史下载 API 已在合成 staging 的候选 Web 验证。客户端新增了带条件头的 Web 上传和可复用 `opId` 的传输函数，但尚未接入书库操作及持久离线队列。正式 staging Web 仍为旧镜像；旧上传接口此刻仍可覆盖，不能宣称兼容边界生效。通用下载的活动头解析、旧上传拒绝、删除墓碑、浏览器和原生客户端、multipart、真实双设备与崩溃测试仍未完成。
